# PM Knowledge Base — RAG over your PM library

Chat with your PM book library. Answers are synthesized across every indexed
source, cite books by name, call out where authors disagree, and export to Word
or PDF.

## Stack
- **Backend:** FastAPI + LangChain
- **LLM:** Groq Cloud running `qwen/qwen3.6-27b`
- **Vector DB:** Qdrant Cloud (managed, free tier)
- **Metadata DB:** SQLite
- **Frontend:** React + Vite + Tailwind, streaming chat over SSE

### Where your data goes

Two managed services are involved, so this is not an offline setup:

- **Groq** receives your question plus the retrieved book excerpts on every query.
- **Qdrant Cloud** stores your document embeddings.

Your uploaded source files stay on your machine (`backend/data/uploads`), as does
the SQLite metadata DB. If you need a fully local setup, both pieces can be
swapped — Qdrant runs fine in a container, and any OpenAI-compatible local server
can replace Groq in `backend/app/llm.py`.

Embeddings are computed **locally** (`BAAI/bge-small-en-v1.5` via fastembed), so
your document text is only sent out as the excerpts attached to a question.

You need **Docker Desktop** — it builds and runs everything else (Python, Node)

Unzip the project folder you downloaded, `cd` into it, then turn it into a

cd pm-rag-knowledge-base

Before that first `git add .`, check `.gitignore` covers **every** secret-bearing
file. It currently lists `.env`, but editor leftovers like `.env.save` and
`.env.swp` hold the same keys and are *not* matched. Either delete them or widen
the pattern to `.env*` with a `!.env.example` exception.

## 3. Set up your accounts (both free)

Copy `.env.example` to `.env` in the project root, then fill in the values below:

```bash
cp .env.example .env
```

**Groq** — runs the LLM. Sign up at https://console.groq.com, create an API key,
and set `GROQ_API_KEY`.

**Qdrant Cloud** — stores the vectors.

1. Sign up at https://cloud.qdrant.io
2. Create a cluster (the free tier — 1GB — is plenty for a personal library).
3. Copy the cluster URL (looks like `https://xxxxx.cloud.qdrant.io`) and
   generate an API key.
4. Set `QDRANT_HOST` and `QDRANT_API_KEY`.

`docker-compose.yml` reads all of these from `.env` automatically — no other
config needed.

## 4. Start everything

```bash
docker compose up --build
```

First run will take a few minutes (downloading base images + installing
Python/Node deps). Leave this running.

Nothing to download for the model itself — it runs on Groq's hardware, so
there's no multi-GB pull and no local RAM requirement.

## The chat UI

The query surface is a chat, not a one-shot search box. Layout is chat-first: the
library and upload form live in a left sidebar, the conversation owns the main
column.

- **Follow-ups work.** Each turn is condensed against the recent history into a
  standalone retrieval query before it hits Qdrant. "Which of those should I cut
  first?" carries almost no searchable signal on its own; it gets rewritten to
  something like `MoSCoW method which tier to cut first deadline`. The rewrite is
  shown above the answer (`searched: …`) so retrieval stays inspectable.
- **Answers stream in** token by token over SSE, with a stop button.
- **Markdown renders** as markdown — the old panel printed raw `**bold**`.
- **Sources collapse** behind a per-answer toggle instead of a permanent wall of
  cards. Copy and Word/PDF export sit on each answer.
- **Reasoning is chosen per question** — see below. Each answer is labelled with
  the mode and why, and an Auto / Quick / Deep switch above the composer overrides
  the guess.
- **History is trimmed** before it's sent back: last 4 messages, assistant replies
  capped at 600 chars (`_HISTORY_TURNS` / `_HISTORY_CHAR_CAP` in `llm.py`). Since
  there is no server-side session, the browser re-sends the whole conversation each
  turn; untrimmed, the prompt crosses the free tier's per-request ceiling around
  turn 5 and every request 413s from then on. Trimmed, it stays flat at ~2k tokens
  no matter how long the chat runs.
- **The topic filter was removed.** With one library and semantic retrieval it
  never earned its place. `topic` is still stored per document and
  `GET /documents?topic=` still filters, but nothing in the UI sends it.

## Reasoning modes

Reasoning costs ~2.1–2.9k tokens per answer — around **85% of the output budget** —
and buys better citations and contradiction-spotting. On a plain lookup there is
nothing to reason about, so the effort is chosen per turn. Measured on this shelf:

| Mode | Reserve | Reasoning | Answer | Latency | Billed | Questions/min |
|---|---|---|---|---|---|---|
| Quick | 1,200 | 0 | ~690 tok | ~2s | ~3,100 | 2 |
| Deep | 5,000 | ~2,100 | ~550 tok | ~5–25s | ~6,900 | 1 |

Quick returns a *longer* answer than Deep, because none of its budget is spent on
reasoning you never see.

`llm_quick_max_tokens` has to drop alongside the effort. Groq bills the *reserved*
budget, so `reasoning_effort=none` while still reserving 5,000 would buy nothing —
the reservation is the cost, not the usage.

**Selection is by question intent only** (`_COMPARATIVE` in `llm.py`): words like
*compare, contrast, differ, disagree, versus, tradeoffs, across the books, better
than* route to Deep; everything else to Quick.

Counting how many books the retrieval touched was the obvious second signal, and
it does not work — measured, not assumed. "What is a product roadmap?" (a lookup)
and "Compare how the authors approach prioritization" both return 5 chunks from one
book and 3 from another. Nearly every query on a focused shelf spans 2+ books, so
that rule sent *everything* to Deep and Quick never fired.

## Changing the model

Set `LLM_MODEL` in `.env` and restart. Any chat model Groq serves works —
`curl https://api.groq.com/openai/v1/models -H "Authorization: Bearer $GROQ_API_KEY"`
lists what's available. `/health/llm` will report `unavailable` if you set a
name Groq doesn't serve.

**If you switch to a non-reasoning model** (e.g. `llama-3.3-70b-versatile`), also
set `llm_reasoning_format` and `llm_reasoning_effort` to `None` in
`backend/app/config.py` — those models reject the reasoning parameters.

Reasoning models need `llm_max_tokens` large enough to cover *both* the internal
reasoning and the answer. Measured on `qwen/qwen3.6-27b`: ~2,100–2,900 reasoning
tokens plus ~550 of answer. The provider default of 2048 doesn't even cover the
reasoning, so the answer comes back truncated or empty. It is set to **5000**, near
the top of what the free tier's per-request ceiling allows.

## Groq free-tier rate limits

Two limits run at once. Both are token buckets that refill continuously — not
counters that reset on the hour or at midnight. Read the live values off any
response:

```bash
curl -sD - -o /dev/null https://api.groq.com/openai/v1/chat/completions \
  -H "Authorization: Bearer $GROQ_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"qwen/qwen3.6-27b","messages":[{"role":"user","content":"hi"}],"max_completion_tokens":16}' \
  | grep -i x-ratelimit
```

| Limit | Size | Refill | Binds when |
|---|---|---|---|
| Tokens | 8,000 | ~133/second (8,000/min) | always, in practice |
| Requests | 1,000 | 1 per 86.4s (= 1,000/day) | only under ~8h of nonstop chat |

**Groq counts the *reserved* `max_completion_tokens`, not what's returned.** So a
Deep answer costs ~1,900 prompt + 5,000 reserved ≈ 6,900 against the 8,000/min
budget — one per minute. A Quick answer costs ~3,100 — two per minute.

Two consequences worth internalising:

- A **single request** must satisfy `prompt + reserved ≤ 8,000` or it can never
  succeed, no matter how long you wait. `llm_max_tokens: 8192` exceeds this on its
  own — that setting 413s on every request, permanently.
- A **follow-up costs two requests**, not one: the condense call plus the answer
  call. Irrelevant against 1,000/day, but worth knowing.

Rate-limit failures now surface in the chat as a readable message ("the free tier
allows roughly one question per minute — wait a moment and ask again") instead of a
bare HTTP 500. Nothing retries or backs off automatically; worth adding if you use
this heavily. Upgrade at https://console.groq.com/settings/billing.

## API routes

| Method | Route | Purpose |
|---|---|---|
| GET | `/documents` | List documents, optional `?topic=` filter |
| POST | `/documents/detect-metadata` | Preview endpoint: guess title/author/topic from a file's first pages |
| POST | `/documents/upload` | Upload one or many files + metadata |
| DELETE | `/documents/{id}` | Remove a document and its vectors |
| POST | `/chat/stream` | Multi-turn chat, streamed as SSE |
| POST | `/query` | One-shot ask → answer + sources + timestamp (non-streaming) |
| POST | `/answer` | Same, but answer text only |
| POST | `/export` | Generate PDF or DOCX from a Q&A |
| GET | `/health`, `/health/llm`, `/health/db` | Status checks |

### `/chat/stream`

Body is `{ messages: [{role, content}, …], mode: "auto" | "quick" | "deep" }`.
The last message must be from the user. Events, in order:

| Event | Payload |
|---|---|
| `sources` | `{sources: [...], search_query, mode, mode_reason}` — arrives before the first token |
| `token` | `{t: "…"}` — one per delta |
| `done` | `{}` |
| `error` | `{detail: "…"}` — replaces `done`; also used for rate limits and empty answers |

## Notes

- **Delete documents:** the "Your shelf" panel lists every indexed document with a
  Delete button (two-step confirm). Deleting removes the file, its SQLite row, and
  its vectors in Qdrant.
- **Vector DB location:** uses **Qdrant Cloud** (managed, not local). Nothing runs
  in a local `qdrant` container.
- **Storage limit:** enforced at 1GB (`MAX_STORAGE_MB`) — uploads are rejected once
  you hit it. This tracks your uploaded source files on disk, not the Qdrant Cloud
  storage, so keep an eye on your Qdrant Cloud plan's own limits too.
- **First query after startup is slow** (~25s vs ~7s). The embedding model loads on
  first use. Subsequent queries are normal speed. This also applies after every
  backend rebuild.

### Checking for orphaned vectors

If an upload is interrupted, or a document row disappears without its vectors being
cleaned up, Qdrant keeps chunks whose `document_id` no longer exists in SQLite. They
still get retrieved, so a stale duplicate of a book competes for the top-k slots and
skews answers toward it. To audit:

```bash
docker exec -i pmrag-backend python - <<'PY'
import collections
from app.vector_store import get_client
from app.config import settings
from app.database import SessionLocal
from app import models

c = get_client(); tally = collections.Counter(); off = None
while True:
    pts, off = c.scroll(settings.qdrant_collection, limit=512, offset=off, with_payload=True)
    for p in pts:
        tally[((p.payload or {}).get('metadata') or {}).get('document_id')] += 1
    if off is None: break
known = {d.id for d in SessionLocal().query(models.Document).all()}
for k, v in tally.most_common():
    print(f"{str(k):<18}{v:>5}   {'ok' if k in known else 'ORPHAN'}")
PY
```

Remove an orphan with `delete_document_chunks("<document_id>")` from the same shell.

## Local dev without Docker (optional, faster iteration)

**Use Python 3.11.** `fastembed==0.3.6` has no build for 3.12+, so `pip install`
fails outright on a newer interpreter. The Docker image pins `python:3.11-slim`
for this reason.

```bash
# Terminal 1: Backend (uses Groq + Qdrant Cloud, set up in step 3 above)
cd backend
python3.11 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp ../.env.example .env   # fill in GROQ_API_KEY / QDRANT_HOST / QDRANT_API_KEY
uvicorn app.main:app --reload

# Terminal 2: Frontend
cd frontend
npm install
npm run dev
```

If port 8000 is already taken, `uvicorn app.main:app --reload --port 8010` and
set `VITE_API_URL=http://localhost:8010` for the frontend.

### docker-compose.override.yml

`docker-compose.override.yml` is untracked and loaded automatically by Docker
Compose. This checkout's copy does two things:

1. **Publishes the backend on 8010** instead of 8000 (the container still listens
   on 8000 internally), because port 8000 was already taken on this machine. It also
   points the frontend's `VITE_API_URL` at the new port.
2. **Mounts `frontend/src` into the container.** Both images `COPY` their source in
   at build time, so without a mount, edits are invisible to the running container —
   Vite happily serves the stale copy baked into the image and you debug code that
   isn't running. The mount is what makes hot reload work.

**Backend code is still baked in.** Python changes need a rebuild, not a restart:

```bash
docker compose up --build -d backend   # picks up backend code changes
docker compose restart backend         # does NOT — restarts the old image
```
